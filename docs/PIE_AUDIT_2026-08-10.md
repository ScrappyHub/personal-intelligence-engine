## 1. What PIE is

PIE is a Windows / PowerShell, offline-first *personal AI runtime* (~19.8k LOC across
`scripts/*.ps1`). It runs local models through Ollama, records governed agent/chat sessions
with hash-chained transcripts, and produces cryptographically verifiable "run packets" under
Packet Constitution v1 Option A. Delivery surfaces are a CLI (`pie.ps1`), a loopback web
workbench (`workbench/`), and an Electron desktop wrapper (`desktop/`).

Canonical guarantees (`SPEC.md`, `LAW.md`): offline-first operation, canonical-bytes hashing,
content addressing, append-only hash-linked run ledger, optional NeverLost signing with
namespace enforcement, and no silent drift.

## 3. What is working (ready today)

- **Governed CLI + local inference.** `pie.ps1` dispatches runtime, agent, chat, workbench,
  package, session, haai, doctor, and integrations subcommands against a live Ollama host.
- **Integrity-bound sessions.** New sessions bind repo path/identity, backend, model digest,
  and goal; conversation turns use an indexed SHA-256 chain, parsed fail-closed; concurrent
  writers rejected via exclusive locks; legacy sessions readable but non-executing.
- **Tier-0 packet pipeline.** Real FULL_GREEN freeze on record
  (`freeze/PIE_TIER0_FREEZE_MANIFEST_v1.txt`, first green 2026-03-08): seal → build Option-A
  packet → sign → verify, with deterministic positive/negative vectors. Canonical-bytes
  hashing and non-mutating verification hold.
- **Encrypted session backup/restore.** Full-payload AES-256-GCM with scrypt-derived keys,
  fresh salt/nonce/tag per export; negative tests reject corruption, traversal, and bad
  passphrases before restore.
- **HAAI evidence export.** Explicit, idempotent, independently re-verifies packet hashes,
  writes only inside the bound PIE session.

## 4. Gaps and unfinished pieces

### 4.1 The Tier-0 run backend is still a stub (highest impact) — PARTIALLY ADDRESSED 2026-08-10
`scripts/pie_run_v1.ps1` originally emitted only `PIE_STUB_OUTPUT ...` with the comment
"replace with engine adapters," and the `engine/` directory was **empty**, contradicting
`SPEC.md` (which places backend adapters under `engine/`).

Addressed in this pass:
- Created the engine layer: `engine/README.md` (adapter design rules) and
  `engine/adapters/ollama/PIE_ENGINE_ADAPTER.v1.json` (adapter contract).
- Wired an **opt-in** `-Backend` parameter into `pie_run_v1.ps1`. Default `stub` is byte-identical
  to prior behavior, so the frozen Tier-0 vectors are untouched. `-Backend ollama` seals **real**
  local generations through the existing loopback adapter, fail-closed with `PIE_ENGINE_*`
  tokens (never silently falls back to stub).
- The recording law (input/output/params hashing, append-only hash-linked ledger, plaintext
  artifacts) and the sealed-model-manifest binding are preserved unchanged; the versioned
  `run_record.v1` schema was intentionally **not** mutated.

Still open: `llama.cpp` (GGUF), `vLLM`, and `onnx` adapters named in `SPEC.md` remain
unimplemented; and real-backend runs are explicitly **not** cross-host reproducible (drift
evaluation is a release blocker). Verification of the new opt-in path must be run on Windows
(see §8).

### 4.2 Local model registry is placeholder-only
`models/mistral-7b/weights.gguf` is 18 bytes. Real inference depends entirely on an external
Ollama installation, not the content-addressed local weight registry described in `SPEC.md`.

### 4.3 Desktop and hosted are not release-ready

is contract-only with the production gateway explicitly unimplemented. Open release blockers

## 5. What PIE is ready to do now

Run local models offline through the governed CLI and workbench; hold integrity-bound
agent/chat sessions with hash-chained transcripts; produce and independently verify Tier-0
evidence packets; and export/restore encrypted session backups. It is **not** ready to ship as
a desktop application or hosted service, and the verifiable pipeline does not yet seal real
model output.
